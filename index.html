Построковий розбір усіх 20 команд звіту (Шпаргалка)

Ключові команди macOS та FreeBSD, їх функції та параметри
🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

У практичній частині звіту я використав рівно 20 діагностичних команд UNIX (13 у macOS та 7 у FreeBSD), щоб на низькому рівні порівняти архітектуру ядра, процеси, файлові системи APFS і ZFS, а також підсистеми безпеки.

💻 ПОЯСНЕННЯ КОДУ, ФУНКЦІЙ ТА ПАРАМЕТРІВ
1. sw_vers
Функція: виводить назву, версію та номер збірки macOS. Результат: macOS 27.2 (Build 26B123).
2. uname -a
Функція: виводить інформацію про ядро ОС. Параметр: -a (all — повний вивід: назва ядра Darwin 27.2.0, версія XNU xnu-13432.41.4, архітектура arm64).
3. sysctl kern.ostype kern.osrelease
Функція: читає параметри стану ядра з MIB-дерева. Параметри: kern.ostype (тип ядра = Darwin), kern.osrelease (реліз = 27.2.0).
4. sysctl -n machdep.cpu.brand_string
Функція: повертає назву моделі процесора. Параметри: -n (не виводити назву ключа, тільки значення), machdep.cpu.brand_string (Apple M1 Pro).
5. sysctl hw.ncpu hw.memsize
Функція: апаратні характеристики. Параметри: hw.ncpu (кількість логічних ядер = 10), hw.memsize (обсяг ОЗП у байтах = 17179869184, тобто 16 ГБ).
6. ps -axco pid,user,%cpu,%mem,comm | head -12
Функція: список запущених процесів. Параметри: -a (усіх користувачів), -x (включно з фоновими демонами без термінала), -c (тільки ім'я виконуваного файлу), -o (формат колонок). Доводить, що PID 1 — launchd.
7. kmutil showloaded --list-only
Функція: менеджер розширень ядра (Kernel Management Utility). Параметри: showloaded (показати завантажені в ядро kext/kpi), --list-only (компактний список без залежностей). Показує три складові XNU: kpi.mach, kpi.bsd, kpi.iokit.
8. launchctl list | head -8
Функція: керування демонами та агентами підсистеми launchd. Параметр: list (виводить таблицю PID, код завершення Status та назву служби Label).
9. diskutil list internal
Функція: утиліта керування дисками macOS. Параметри: list (схема розділів), internal (тільки внутрішній SSD). Показує фізичний диск disk0 і синтезований контейнер APFS disk3.
10. mount | grep -E 'apfs'
Функція: виводить таблицю змонтованих файлових систем і фільтрує APFS. Показує прапорці системного тому: sealed (криптографічно запечатаний) та read-only (лише читання).
11. df -h / /System/Volumes/Data
Функція: оцінка вільного місця (disk free). Параметр: -h (human-readable — у гігабайтах Gi). Доводить спільний пул вільного місця (82 Gi) для кореня / і тому даних.
12. csrutil status && spctl --status && fdesetup status
Функція: перевірка трьох механізмів безпеки macOS: csrutil status — статус SIP (System Integrity Protection); spctl --status — статус політики безпеки Gatekeeper; fdesetup status — статус повного шифрування диска FileVault.
13. codesign --verify --verbose /Applications/Safari.app && ls -lO /System
Функція: codesign --verify --verbose перевіряє цілісність цифрового підпису програми Apple; ls -lO з прапорцем -O виводить системні прапорці файлів (показує прапорець restricted, який захищає каталоги навіть від root).
14. [FreeBSD] freebsd-version -kru
Функція: виводить версію FreeBSD. Параметри: -k (встановлене ядро), -r (запущене ядро), -u (користувацьке середовище userland). Усі три = 15.1-RELEASE.
15. [FreeBSD] kldstat && kldload if_bridge
Функція: робота з модулями монолітного ядра (Kernel Linker). kldstat виводить таблицю завантажених модулів (kernel, zfs.ko); kldload if_bridge динамічно підвантажує модуль мережевого моста if_bridge.ko та bridgestp.ko без перезавантаження.
16. [FreeBSD] zpool status zroot && zfs list
Функція: діагностика ZFS. zpool status zroot перевіряє стан пулу (ONLINE, 0 помилок READ/WRITE/CKSUM); zfs list -o name,used,avail,mountpoint виводить датасети пулу.
17. [FreeBSD] zfs snapshot zroot/ROOT/default@lab1 && zfs list -t snapshot
Функція: створює миттєвий Copy-on-Write знімок кореневої ФС з ім'ям @lab1; ключ -t snapshot виводить список знімків (розмір USED = 0B).
18. [FreeBSD] jail -c name=lab1 path=/ host.hostname=lab1-jail persist
Функція: створює ізольований контейнер FreeBSD Jail. Параметри: -c (create), name=lab1 (ім'я), path=/ (корінь), host.hostname=... (власне ім'я хоста), persist (не видаляти автоматично без процесів).
19. [FreeBSD] jls && jexec lab1 ps ax && jail -r lab1
Функція: jls (jail list) показує активні jails (JID 3); jexec lab1 ps ax запускає ps ax всередині jail (бачить лише власний процес з прапорцем J); jail -r lab1 (-r remove) видаляє jail.
20. [FreeBSD] pkg -v && pkg info | wc -l && pkg info fastfetch
Функція: бінарний пакетний менеджер FreeBSD. -v — версія (2.8.4), pkg info | wc -l — підрахунок усіх встановлених пакетів (496, включно з базовою системою FreeBSD 15 PkgBase).
📊 ПОЯСНЕННЯ РЕЗУЛЬТАТІВ (ЧОМУ ТАК ВИЙШЛО)

Головний висновок з коду: Усі 20 команд наочно доводять: попри спільні утиліти BSD (sysctl, ps, mount, df), macOS має гібридне ядро XNU (kmutil), ініціалізатор launchd і файлову систему APFS, тоді як FreeBSD має модульне монолітне ядро (kldstat), класичний init, файлову систему ZFS і контейнерну ізоляцію jails.

Загальна характеристика і призначення

Сторінки 3–4 звіту · Таблиця 1 · Розділ 3–4
🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

У таблиці 1 наведено порівняльну характеристику. macOS вийшла у 2001 році на базі NeXTSTEP, має гібридне ядро XNU (мікроядро Mach + шар BSD + об'єктно-орієнтована підсистема драйверів IOKit), пропрієтарну ліцензію з відкритим ядром Darwin і офіційну сертифікацію UNIX 03.

FreeBSD з'явилася у 1993 році, має монолітне ядро з динамічно завантажуваними модулями (kld), вільну двопунктову BSD-ліцензію і підтримує багато архітектур (amd64, arm64, riscv64). За призначенням macOS — це робочі станції та ноутбуки Apple, а FreeBSD — високонавантажені сервери, системи зберігання даних і маршрутизатори (на ній працюють сервери CDN Netflix, ОС консолей PlayStation 4/5 та брандмауер pfSense).

📊 ПОЯСНЕННЯ РЕЗУЛЬТАТІВ (ЧОМУ ТАК ВИЙШЛО)

Пояснення результатів Таблиці 1: Сертифікація UNIX 03 у macOS означає повну відповідність стандарту Single UNIX Specification v3, а 2-clause BSD ліцензія у FreeBSD дозволяє корпораціям (Apple, Sony, Netflix, Juniper) брати код FreeBSD у закриті продукти без вимоги відкривати власні напрацювання (на відміну від GPL у Linux).

Практика macOS: Система, ядро XNU та Пам'ять

Сторінки 5–6 звіту · Рисунки 1–3
🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

Щоб перевірити теорію на практиці, я дослідив обидві ОС вживу. Спочатку macOS 27.2 на своєму MacBook Pro з процесором M1 Pro.

На рисунку 1 утиліти sw_vers, uname -a та sysctl показують ядро Darwin 27.2.0 (гілка XNU 13432) для архітектури ARM64, 10 ядер процесора і 16 ГБ оперативної пам'яті. На рисунку 2 команда kmutil showloaded демонструє три ключові інтерфейси ядра: com.apple.kpi.mach, com.apple.kpi.bsd та com.apple.kpi.iokit — це практичний доказ гібридної архітектури XNU. А команда ps показує, що першим процесом системи з PID 1 є launchd.

На рисунку 3 у програмі «Моніторинг системи» видно механізм стисненої пам'яті (Compressed Memory): замість того, щоб одразу скидати неактивні сторінки у swap на SSD, ядро XNU стискає їх у швидкій оперативній пам'яті.

💻 ПОЯСНЕННЯ КОДУ, ФУНКЦІЙ ТА ПАРАМЕТРІВ
sw_vers && uname -a
Виводить версію macOS 27.2 (26B123) та ядро Darwin 27.2.0 XNU arm64.
sysctl kern.ostype kern.osrelease hw.ncpu hw.memsize
Виводить тип ядра Darwin, 10 ядер CPU та 17179869184 байт (16 ГБ) ОЗП.
ps -axco pid,user,%cpu,%mem,comm | head -12
Показує процес PID 1 — launchd (єдиний менеджер служб і демонів macOS).
kmutil showloaded --list-only 2>/dev/null | awk '{print $1, $6, $7}' | head -10
Виводить завантажені компоненти ядра: kpi.bsd, kpi.iokit, kpi.mach.
📊 ПОЯСНЕННЯ РЕЗУЛЬТАТІВ (ЧОМУ ТАК ВИЙШЛО)

Пояснення результатів (Рис. 1–3): У гібридному ядрі XNU мікроядро Mach відповідає за планувальник потоків, віртуальну пам'ять та міжпроцесну взаємодію (IPC); шар BSD — за POSIX API, файлову систему, мережу і права доступу; IOKit — за драйвери пристроїв. Усі три частини працюють в одному адресному просторі ядра заради швидкодії.

Практика macOS: Файлова система APFS та Безпека

Сторінки 7–8 звіту · Рисунки 4–7
🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

Далі я дослідив файлову систему APFS (рисунки 4–5). Команда diskutil list internal показує, що фізичний SSD містить контейнер APFS disk3 на 494 ГБ, у якому живуть 6 логічних томів: системний Macintosh HD, том користувацьких даних Data, Preboot, Recovery та VM. Вони ділять спільний пул вільного простору (Space Sharing).

Команда mount показує, що кореневий том / змонтований не напряму з диска, а з криптографічно підписаного незмінного знімка APFS з прапорцями sealed, read-only.

На рисунках 6–7 перевірено багаторівневу безпеку macOS: csrutil status підтверджує увімкнений захист цілісності системи SIP, spctl --status — роботу Gatekeeper, fdesetup status — апаратне шифрування диска FileVault, а ls -lO /System показує прапорець restricted, який забороняє модифікацію системних каталогів навіть суперкористувачу root.

💻 ПОЯСНЕННЯ КОДУ, ФУНКЦІЙ ТА ПАРАМЕТРІВ
diskutil list internal | head -22
Виводить структуру контейнера APFS disk3 та всі логічні томи.
mount | grep -E 'apfs' | head -5
Показує монтування кореня / як apfs, sealed, local, read-only, journaled.
df -h / /System/Volumes/Data
Показує однаковий доступний простір (Avail 82Gi) для системного тому і тому даних.
csrutil status && spctl --status && fdesetup status && ls -lO /System | head -6
Перевіряє SIP, Gatekeeper, FileVault і прапорець restricted.
📊 ПОЯСНЕННЯ РЕЗУЛЬТАТІВ (ЧОМУ ТАК ВИЙШЛО)

Пояснення результатів (Рис. 4–7): Концепція Signed System Volume (SSV) у macOS гарантує, що навіть якщо зловмисник отримає права root, він не зможе змінити системні файли, бо корінь змонтований у режимі read-only із запечатаного знімка, хеш-дерево якого перевіряється чіпом Apple Silicon під час завантаження.

Що показати: На рис. 4 рядок /dev/disk3s1s1 on / (apfs, sealed, local, read-only), а на рис. 6 — прапорець restricted.

Практика FreeBSD: Система і модульне ядро

Сторінки 9–10 звіту · Рисунки 8–10
🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

Другу частину дослідження я провів у FreeBSD 15.1-RELEASE для arm64 у віртуальній машині QEMU (рисунки 8–9). Команда freebsd-version -kru вивела три однакових рядки 15.1-RELEASE — для встановленого ядра, запущеного ядра та призначеного для користувача оточення (userland). Це ключова відмінність FreeBSD від Linux: тут ядро і всі базові утиліти розробляються однією командою як єдина цілісна система.

На рисунку 10 я перевірив модульність монолітного ядра. Спочатку kldstat показав лише ядро kernel і модуль файлової системи zfs.ko. Потім командою kldload if_bridge я прямо під час роботи системи, без перезавантаження, підвантажив модуль мережевого моста — і у виводі kldstat одразу з'явилися if_bridge.ko та bridgestp.ko. Висновки та Контрольні питання (ЛР 1)

Сторінки 16–20 звіту · Відповіді на питання
🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

Висновки: Ми на практиці переконалися, що macOS і FreeBSD, маючи спільне коріння BSD, еволюціонували під абсолютно різні задачі. macOS — це еталонна захищена настільна система з гібридним ядром XNU та APFS для кінцевого користувача і розробника. FreeBSD — це надійна відкрита серверна платформа з модульним монолітним ядром, ZFS та Jails. Отже, універсальної «найкращої» ОС не існує — вибір завжди визначається задачею.

1. Дайте визначення поняття «операційна система».

Операційна система (ОС) — це комплекс системних управляючих і обробних програм, який керує апаратними ресурсами комп'ютера (процесором, пам'яттю, пристроями вводу-виводу), організовує зберігання файлів і виконання прикладних програм та надає користувачу і програмам зручний інтерфейс (CLI, GUI, API).

2. Назвіть приклади прикладного та системного ПЗ.

Системне ПЗ: операційні системи (macOS, FreeBSD, Windows, Linux), драйвери пристроїв, завантажувачі (UEFI, GRUB), утиліти обслуговування (diskutil, zpool), компілятори. Прикладне ПЗ: офісні пакети (Word, Excel), браузери (Safari, Chrome), графічні й відеоредактори (Photoshop, Final Cut), месенджери, ігри.

3. Дайте визначення понять «API», «драйвер», «ядро».

API (Application Programming Interface) — набір функцій, структур і правил, через які прикладні програми звертаються до сервісів ОС (наприклад, POSIX API, Win32 API, Cocoa). Драйвер — програмний модуль ядра або системи, який переводить стандартні запити ОС у команди конкретного фізичного пристрою. Ядро (Kernel) — центральна частина ОС, що працює у привілейованому режимі процесора (Ring 0 / EL1) і керує процесами, пам'яттю, перериваннями та системними викликами.

4. Наведіть способи класифікації ОС.

1) За архітектурою ядра: монолітні (FreeBSD, Linux), мікроядерні (QNX, MINIX 3), гібридні (macOS XNU, Windows NT). 2) За кількістю задач і користувачів: однозадачні/однокористувацькі (MS-DOS) та багатозадачні/багатокористувацькі (UNIX, Windows). 3) За призначенням: настільні, серверні, мобільні, вбудовані, ОС реального часу (RTOS). 4) За ліцензією: пропрієтарні та відкриті (Open Source).

5. Вимоги до сучасних ОС.

Надійність і відмовостійкість, безпека (ізоляція та розмежування прав), ефективність (мінімальні накладні витрати), розширюваність (модульність), переносимість між архітектурами (ARM, x86), сумісність, масштабованість та зручність інтерфейсу.

6. Основні функції ОС.

Керування процесами і потоками (планування CPU, синхронізація), керування оперативною і віртуальною пам'яттю, керування файловою системою, керування пристроями вводу-виводу, захист і безпека, мережева взаємодія, облік ресурсів та надання інтерфейсів (GUI/CLI/API).

Висновки: Я опанував повний цикл роботи з VirtualBox 7.2 на macOS Apple Silicon: створив ВМ Zahorskyi_Win, встановив Windows 11 ARM64, налаштував інтеграцію через Guest Additions, вирішив проблему з драйвером мережі через паравіртуальний адаптер virtio-net і дослідив внутрішню структуру файлів ВМ, диференціальних знімків та OVA-експорту. Дякую, готовий відповісти на запитання!

1. Які переваги та недоліки використання ВМ?

Переваги: одночасна робота кількох ОС на одному ПК без перезавантаження; повна ізоляція гостя від хоста (безпека при тестуванні ПЗ чи вірусів); миттєві знімки стану (snapshots); легке клонування та перенесення однією папкою або файлом .ova. Недоліки: накладні витрати на віртуалізацію (нижча продуктивність диска і 3D-графіки); ОЗП і ядра CPU забираються у хоста на час роботи ВМ; залежність гіпервізора від архітектури процесора хоста (ARM запускає тільки ARM); великий розмір образів на диску.

2. Які можливості надають гостьові доповнення ВМ (Guest Additions)?

Це набір драйверів ядра (VBoxGuest, VBoxSF, VBoxWddm) і системних служб (VBoxService, VBoxTray), що встановлюються всередину гостьової ОС. Вони забезпечують: двонаправлений буфер обміну, drag'n'drop, спільні теки (Shared Folders), інтеграцію курсора миші без захоплення клавішею Host, автозміну роздільної здатності екрана ВМ при розтягуванні вікна, синхронізацію часу з хостом та керування процесами гостя через VBoxManage guestcontrol.

3. На що впливає об’єм оперативної пам’яті, виділеної для ВМ?

Він безпосередньо визначає швидкодію гостьової ОС та кількість програм, які можна в ній відкрити без інтенсивного використання файлу підкачки (pagefile.sys). Однак ця пам'ять фізично резервується в ОЗП хоста на час роботи ВМ: якщо виділити більше 50–60% пам'яті хоста, почне гальмувати вже сама основна ОС. Крім того, від обсягу ОЗП прямо залежить розмір файлу дампу пам'яті .sav при збереженні стану чи онлайн-знімку.

4. В чому полягає різниця між динамічним і фіксованим ВЖД?

Динамічний диск (Standard) спочатку займає мінімум місця і росте на диску хоста в міру запису нових секторів у гостьовій ОС (у нас з 64 ГБ зайнято лише 14,9 ГБ), але трохи повільніший при розширенні і схильний до фрагментації. Фіксований диск (Fixed) одразу при створенні резервує всі 64 ГБ на SSD хоста, створюється довше, зате не фрагментується і забезпечує вищу швидкість запису.

5. Що таке знімки ВМ (Snapshots) і де вони знаходяться?

Знімок — це зафіксований на певний момент часу стан дисків, конфігурації (.vbox) і (для увімкненої ВМ) оперативної пам'яті. При створенні знімка базовий диск .vdi переходить у режим тільки для читання («заморожується»), а в папці Snapshots створюється диференціальний (різницевий) диск {UUID}.vdi, куди пишуться всі подальші зміни, а також файл дампу пам'яті *.sav та *.nvram.

6. Яким чином і для чого здійснюється експорт та імпорт ВМ?

Експорт використовується для перенесення ВМ на інший комп'ютер, в інший гіпервізор (VMware, Proxmox) або для архівного резервного копіювання за відкритим стандартом OVF. Виконується на вимкненій ВМ через «Файл -> Експорт конфігурацій» (або VBoxManage export) і пакує XML-опис .ovf, стиснутий диск .vmdk та контрольні суми .mf в один архів .ova. Імпорт («Файл -> Імпорт конфігурацій») розпаковує .ova і реєструє готову ВМ.

7. Які типи мережевих підключень дозволяє налаштовувати ВМ?

1) NAT (за замовчуванням: ВМ має вихід в Інтернет через IP хоста, але ізольована ззовні); 2) Мережа NAT (NAT Network — спільна підмережа для кількох ВМ з виходом в Інтернет); 3) Мережевий міст (Bridged Adapter — ВМ підключається напряму до фізичного роутера і отримує власний IP у локальній мережі); 4) Внутрішня мережа (Internal Network — ізольована мережа тільки між ВМ); 5) Віртуальний адаптер хоста (Host-Only — зв'язок тільки між хостом і ВМ без Інтернету); 6) Універсальний драйвер (Generic Driver); 7) Не підключено.

8. Які папки та файли створюються для супроводу ВМ?

У каталозі ~/VirtualBox VMs/<Ім'я_ВМ> створюються: <Ім'я>.vbox (XML-конфігурація ВМ), <Ім'я>.vbox-prev (резервна копія конфігурації), <Ім'я>.vdi (базовий віртуальний жорсткий диск), <Ім'я>.nvram (пам'ять прошивки UEFI), папка Logs (журнали VBox.log), папка Snapshots (диференціальні диски {UUID}.vdi та файли стану пам'яті *.sav). Глобальний реєстр усіх ВМ лежить у ~/Library/VirtualBox/VirtualBox.xml.

У лабораторній роботі № 3 я налаштовував віртуальну машину як через GUI, так і через VBoxManage, а всі перевірки всередині гостьової Ubuntu 24.04 виконував стандартними утилітами Linux у терміналі bash. Ось построковий розбір усіх 20 команд звіту.

💻 ПОЯСНЕННЯ КОДУ, ФУНКЦІЙ ТА ПАРАМЕТРІВ
1. VBoxManage createvm --name Zahorskyi_Ubuntu --ostype Ubuntu24_LTS_arm64 --register --default
Функція: створює ВМ з профілем Ubuntu 24.04 ARM64. Параметри: --register (реєструє в VirtualBox), --default (створює базовий набір контролерів за замовчуванням).
2. VBoxManage modifyvm Zahorskyi_Ubuntu --memory 4096 --cpus 4 --vram 128 --clipboard-mode bidirectional --drag-and-drop bidirectional
Функція: виділяє 4 ГБ ОЗП, 4 ядра CPU, 128 МБ відеопам'яті та вмикає двонаправлений буфер обміну і drag'n'drop.
3. VBoxManage modifyvm Zahorskyi_Ubuntu --nic1 nat --usb-xhci on --boot1 disk --boot2 dvd --boot3 none --boot4 none
Функція: вмикає мережевий адаптер 1 у режимі nat, контролер USB 3.0 (--usb-xhci on) та задає чергу завантаження: 1) диск, 2) DVD.
4. VBoxManage createmedium disk --filename Zahorskyi_Ubuntu.vdi --size 25600 --format VDI
Функція: створює динамічний віртуальний диск формату VDI обсягом 25 600 МБ (25 ГБ).
5. VBoxManage storageattach Zahorskyi_Ubuntu --storagectl SATA --port 0 --type hdd --medium Zahorskyi_Ubuntu.vdi
Функція: підключає основний VDI-диск до порту 0 контролера SATA (AHCI). Ми спеціально перенесли диск із VirtIO-SCSI на SATA AHCI, щоб уникнути помилки VERR_SSM_LOAD_CONFIG_MISMATCH при відновленні збереженого стану.
6. VBoxManage storageattach Zahorskyi_Ubuntu --storagectl SATA --port 1 --type dvddrive --medium ubuntu-24.04.5-desktop-arm64.iso
Функція: монтує інсталяційний ISO-образ Ubuntu 24.04.5 у віртуальний оптичний привід на порту 1 контролера SATA.
7. VBoxManage sharedfolder add Zahorskyi_Ubuntu --name lab3_shared --hostpath ~/VMs/oslabs/lab3_shared --automount
Функція: додає спільну теку хоста macOS з автоматичним монтуванням у гостьовій Ubuntu (--automount).
8. VBoxManage storagectl Zahorskyi_Ubuntu --name USB --add usb && VBoxManage storageattach ... USB_flash.vdi
Функція: створює контролер носіїв USB і підключає до нього віртуальну флешку USB_flash.vdi обсягом 1 ГБ.
9. VBoxManage unattended install Zahorskyi_Ubuntu --iso=ubuntu-24.04.5-desktop-arm64.iso --user=taras --locale=uk_UA --install-additions --start-vm=gui
Функція: запускає автоматичне встановлення Ubuntu з українською локаллю, створює користувача taras і автоматично компілює та ставить модулі Guest Additions 7.2.22.
10. [Ubuntu] lsmod | grep vbox && VBoxControl --version
Функція: перевіряє завантажені модулі ядра Linux (рис. 2). Показує модулі vboxsf (спільні теки) та vboxguest (базовий драйвер інтеграції) версії 7.2.22r175245.
11. [Ubuntu] systemctl status vboxadd-service --no-pager && ps -ef | grep VBoxClient
Функція: перевіряє активність системного демона vboxadd-service (active (running)) і процесів сесії користувача VBoxClient --clipboard, --draganddrop, --vmsvga-session.
12. [Ubuntu] ip -4 addr show && ip route
Функція: мережева діагностика пакета iproute2 (рис. 5). ip -4 addr показує IPv4-адресу 10.0.2.15/24 на інтерфейсі enp0s8; ip route показує маршрут за замовчуванням default via 10.0.2.2.
13. [Ubuntu] ping -c 3 google.com && curl -sI https://ubuntu.com | head -5
Функція: перевірка виходу в Інтернет через NAT. Ключ -c 3 відправляє 3 ICMP-пакети (0% packet loss), а curl -sI (-I — тільки HTTP-заголовки) повертає HTTP/2 200.
14. [Ubuntu] lsusb && lsblk -o NAME,SIZE,TYPE,TRAN,FSTYPE,LABEL,MOUNTPOINT
Функція: перевірка USB-флешки (рис. 6). lsusb бачить VirtualBox USB Harddisk на шині USB 3.0; lsblk показує блоковий пристрій sdb з транспортом TRAN=usb, ФС vfat, міткою USB_FLASH і точкою монтування /media/taras/USB_FLASH.
15. [Ubuntu] echo 'Запис на USB-флешку з Ubuntu (Загорський Т., ІПЗ-31)' > /media/taras/USB_FLASH/usb_test.txt && cat ...
Функція: перевіряє реальний запис і читання даних на змонтованому FAT32 розділі віртуальної USB-флешки.
16. [Ubuntu] lsblk /dev/sr0 -o NAME,SIZE,TYPE,FSTYPE,LABEL,MOUNTPOINT && ls '/media/taras/Ubuntu 24.04.5 LTS arm64'
Функція: перевірка CD/DVD приводу (рис. 7). Показує пристрій sr0 типу rom з файловою системою iso9660 обсягом 3,7 ГБ та каталоги інсталятора (boot, casper, EFI, pool).
17. [Ubuntu] df -hT ~/lab3_shared && cat ~/lab3_shared/from_host_macOS.txt && echo '...' > ~/lab3_shared/from_guest_ubuntu.txt
Функція: перевірка спільної теки (рис. 8). Ключ -T у df -hT показує тип файлової системи vboxsf, після чого виконується двостороннє читання і запис файлів між macOS та Ubuntu.
18. VBoxManage snapshot Zahorskyi_Ubuntu take 'Після налаштування' && ls -lh '~/VirtualBox VMs/Zahorskyi_Ubuntu/Snapshots'
Функція: створює онлайн-знімок стану працюючої ВМ (рис. 12). У теці Snapshots з'являються два диференційні диски {UUID}.vdi та файл стану пам'яті .sav (1,21 ГБ).
19. VBoxManage controlvm Zahorskyi_Ubuntu savestate && VBoxManage startvm Zahorskyi_Ubuntu
Функція: зберігає поточний стан ВМ на диск (стан «Збережено», створюється другий .sav на 1,21 ГБ, рис. 13–14), а startvm миттєво будить ВМ з видаленням тимчасового .sav.
20. VBoxManage export Zahorskyi_Ubuntu -o Zahorskyi_Ubuntu.ova --manifest && tar -tvf Zahorskyi_Ubuntu.ova
Функція: пакує вимкнену ВМ у переносний архів OVF Zahorskyi_Ubuntu.ova (4,84 ГБ) з маніфестом хеш-сум --manifest (рис. 15).

Висновки: Створено і налаштовано віртуальну машину Zahorskyi_Ubuntu з Ubuntu 24.04.5 LTS ARM64. Завдяки модулям ядра Guest Additions (vboxguest, vboxsf) працюють двонаправлений буфер обміну, спільна тека та авторозмір екрана, а також перевірені мережа NAT, віртуальна USB-флешка та завантаження з DVD через UEFI Boot Manager. Досліджено механізм диференційних дисків знімків, збереження стану пам'яті .sav та експорт у формат OVF/OVA. Дякую за увагу!

1. Які переваги та недоліки використання ВМ?

Переваги: одночасний запуск кількох різних ОС на одному комп'ютері; ізоляція гостьової системи від хоста (збій в гості не шкодить основній ОС); миттєвий відкат через знімки (snapshots); проста міграція та резервне копіювання у файл .ova. Недоліки: споживання ОЗП, CPU і диска хоста; нижча продуктивність вводу-виводу та графіки через прошарок гіпервізора; неможливість запуску ОС іншої процесорної архітектури без повільної емуляції.

2. Які можливості надають гостьові доповнення ВМ в Linux?

В Ubuntu Guest Additions компілюють модулі ядра vboxguest і vboxsf та запускають служби vboxadd-service і VBoxClient. Це дає: спільний буфер обміну, спільні теки (файлова система vboxsf), безшовну інтеграцію миші, автоматичну підстройку роздільної здатності екрана (vmsvga), синхронізацію системного годинника з хостом та керування через guestcontrol.

3. На що впливає об’єм оперативної пам’яті, виділеної для ВМ?

Визначає кількість програм, які можуть одночасно працювати в гостьовій ОС без звернення до swap-розділу на диску. Якщо виділити замало — гостьова ОС гальмує через свопінг; якщо забагато — не вистачає пам'яті вже основній ОС (хосту). Рекомендується виділяти не більше 50% фізичної ОЗП хоста (у нас 4 ГБ з 16 ГБ).

4. В чому полягає різниця між динамічним і фіксованим ВЖД?

Динамічний VDI росте поступово в міру заповнення секторами (у нас з 25 ГБ на SSD мака зайнято лише 9,3 ГБ), що економить місце, але сам не стискається після видалення файлів. Фіксований VDI одразу резервує всі 25 ГБ на хості, довше створюється, але не фрагментується і дещо швидший.

5. Що таке знімки ВМ і де вони знаходяться?

Знімок (snapshot) — точка відновлення ВМ, яка фіксує стан дисків, XML-конфігурацію і (якщо ВМ увімкнена) дамп ОЗП. Базовий диск заморожується, а в теці Snapshots створюються диференційні диски {UUID}.vdi (куди пишуться нові зміни) і файл пам'яті *.sav.

6. Яким чином і для чого здійснюється експорт та імпорт ВМ?

Експорт (Файл -> Експорт конфігурацій / VBoxManage export) пакує вимкнену ВМ у відкритий стандарт OVF — один архів .ova (містить XML-опис .ovf, стиснутий диск .vmdk і контрольні суми .mf). Імпорт розгортає готову ВМ на іншому ПК або в іншому гіпервізорі.

7. Які типи мережевих підключень дозволяє налаштовувати ВМ?

NAT (вихід в Інтернет через хост, ВМ за NAT-роутером 10.0.2.2), Мережа NAT (спільна NAT-мережа для кількох ВМ), Мережевий міст (Bridged — ВМ отримує IP від фізичного роутера нарівні з хостом), Внутрішня мережа (Internal — тільки між ВМ), Віртуальний адаптер хоста (Host-Only — тільки між хостом і ВМ), Універсальний драйвер та Не підключено.

8. Які папки та файли створюються для супроводу ВМ?

У каталозі ~/VirtualBox VMs/Zahorskyi_Ubuntu: файл конфігурації .vbox та його копія .vbox-prev, віртуальний жорсткий диск .vdi, файл пам'яті прошивки UEFI .nvram, папка Logs (VBox.log) та папка Snapshots ({UUID}.vdi та *.sav). При експорті створюється архів .ova.

💻 ПОЯСНЕННЯ КОДУ, ФУНКЦІЙ ТА ПАРАМЕТРІВ
1. \Processor(_Total)\% Processor Time
Лічильник Таблиці 1: відсоток часу, протягом якого всі ядра процесора (_Total) виконували не-холості потоки (сума % User Time + % Privileged Time). Нормальний поріг — до 85%.
2. \Processor(_Total)\% Idle Time
Лічильник Таблиці 1: відсоток часу, коли процесор простоював у стані очікування (без взаємодії у нас = 95,031%, під час малювання в Paint впав до 81,835%).
3. \Processor(_Total)\% Privileged Time
Лічильник Таблиці 1: частка часу роботи всіх ядер ЦП у привілейованому режимі ядра (Kernel Mode, Ring 0 / EL1) — системні виклики, драйвери, графіка GDI/DirectX, обробка переривань.
4. \Processor(_Total)\% User Time
Лічильник Таблиці 1: частка часу роботи всіх ядер ЦП у режимі користувача (User Mode, Ring 3 / EL0) — виконання коду самої програми mspaint.exe (у Paint зросла з 2,263% до 10,884%).
5. \Process(Idle)\% Privileged Time (Масштаб 0.1)
Лічильник Таблиці 1: час системного псевдопроцесу «Бездіяльність системи» (Idle) у режимі ядра. Оскільки у ВМ 4 ядра (максимум 400%), встановлено масштаб 0.1 (без взаємодії = 381,551%, з Paint = 331,141%).
6. \Process(Idle)\% User Time
Лічильник Таблиці 1: час процесу Idle у режимі користувача. Завжди дорівнює 0,000%, бо потоки Idle існують виключно всередині ядра ОС (виконують інструкцію зупинки ядра HLT/WFI).
7. \Processor(_Total)\Interrupts/sec (Масштаб 0.01)
Лічильник Таблиці 2: середня кількість апаратних переривань (IRQ), які процесор обробив за секунду. При малюванні мишею в Paint зросла у 19 разів — зі 179,78 до 3 478,23 за секунду!
8. \Processor(_Total)\% Interrupt Time
Лічильник Таблиці 2: відсоток часу процесора, витрачений на виконання процедур обробки переривань (ISR) у режимі ядра. У нас максимум 0,157% і 1,090% (критичний поріг — понад 20–30%).
9. \System\System Calls/sec (Масштаб 0.001)
Лічильник Таблиці 2: частота звернень програм до системних викликів ядра ОС за секунду. У Paint зросла в 11,7 раза — з 2 616,55 до 30 745,73 викликів/с (масштаб 0.001 для відображення на шкалі 0–100).
10. \System\Exception Dispatches/sec
Лічильник Таблиці 2: кількість оброблених ядром виключних ситуацій процесора (exceptions, page faults) за секунду (у нас 1,183 в простої та 4,424 у Paint).

Команда Windows: запускає консоль «Монітор продуктивності» (Performance Monitor). Ключ /sys відкриває одразу окремий монітор у реальному часі.

Без взаємодії 95% часу процесор проводить у стані простою, який обліковується ядерним процесом Idle у режимі ядра. При запуску прикладної програми Paint основні обчислення (малювання фігур і растру) виконуються в непривілейованому режимі користувача (10,88%), а ввід координат миші та вивід графіки на екран передаються через системні виклики (~30,7 тис./с) та апаратні переривання (~3,5 тис./с) у режим ядра (6,32%). Граничні пороги (85% ЦП та 20% переривань) ніде не перевищені. Дякую, готовий відповідати на питання!

1. Характеристики режиму ядра (Kernel / Privileged Mode).

У режимі ядра (Ring 0 на x86 / EL1 на ARM64) код має необмежений доступ до всієї фізичної та віртуальної пам'яті, усіх регістрів процесора і портів вводу-виводу. Тут виконуються виконавча система та мікроядро Windows (ntoskrnl.exe), рівень апаратних абстракцій (HAL), драйвери пристроїв (.sys) та віконно-графічна підсистема (win32k.sys). Будь-яка необроблена помилка у режимі ядра викликає критичний збій усієї ОС (BSOD), тоді як помилка у режимі користувача закриває лише одну програму.

2. Для чого використовується процес Idle в ОС Windows?

Процес «Бездіяльність системи» (System Idle Process, PID 0) містить по одному системному потоку на кожне логічне ядро ЦП з найнижчим можливим пріоритетом. Коли планувальнику Windows немає жодного готового до виконання потоку на ядрі, він перемикає ядро на потік Idle. Його завдання — обліковувати час простою процесора і переводити ядро ЦП в енергоощадний стан інструкціями HLT (x86) або WFI (ARM64), тому весь його час зараховується як % Privileged Time.

3. Як можна прослідкувати за часом роботи у режимі користувача та ядра за допомогою Task Manager?

Потрібно відкрити Диспетчер завдань (Ctrl+Shift+Esc), перейти на вкладку «Продуктивність» (Performance) -> обрати «ЦП» (CPU), клікнути правою кнопкою миші на полі графіка і увімкнути пункт «Показати час ядра» (Show kernel times). Після цього графік розділиться на дві області: світліша показує загальне завантаження (% Processor Time), а темніша всередині неї — частку режиму ядра (% Privileged Time).

4. Які можливості утиліти Performance Monitor з оперативного спостереження за станом ОС?

Дозволяє в реальному часі спостерігати за сотнями лічильників процесора, пам'яті, дисків, мережі та окремих процесів у трьох видах: лінійний графік (Line), гістограма (Histogram bar) або текстовий звіт (Report); масштабувати окремі криві, змінювати колір і товщину ліній, ставити графік на паузу (Freeze Display) та підключатися до віддалених комп'ютерів у мережі.

5. Які можливості утиліти Performance Monitor зі створення звітів?

Дозволяє створювати «Групи збирачів даних» (Data Collector Sets), які у фоновому режимі за розкладом або умовою зупинки записують значення лічильників, трасування подій та конфігурацію реєстру у двійкові журнали (*.blg), текстові таблиці (*.csv, *.tsv) або бази SQL. Збережені логи можна відкривати пізніше, аналізувати мінімум/середнє/максимум, зберігати графіки у *.gif, конвертувати через relog та налаштовувати сповіщення (Alerts) при перевищенні порогів.

6. Які граничні значення лічильників вказують на можливі негаразди в роботі системи?

1) Processor: % Processor Time стабільно вище 85% (при цьому черга потоків System: Processor Queue Length > 2 на ядро) — процесор є вузьким місцем і не справляється з обчисленнями. 2) Processor: % Interrupt Time стабільно вище 20–30% (або % DPC Time > 20%) — свідчить про апаратну несправність пристрою або зависання/помилку в коді драйвера пристрою («шторм переривань»).

Построковий розбір усіх 20 команд cmd.exe зі звіту (Шпаргалка)

Кожна команда звіту ЛР 5, її синтаксис, ключі та призначення
🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

У лабораторній роботі № 5 для створення і дослідження об'єктів файлових систем NTFS та FAT32 у командному інтерпретаторі cmd.exe (від імені адміністратора) використано рівно 20 ключових команд. Ось їх построковий розбір із параметрами.

💻 ПОЯСНЕННЯ КОДУ, ФУНКЦІЙ ТА ПАРАМЕТРІВ
1. cd C:\ && mkdir source_OS && cd source_OS && mkdir labs lects .hidden
Функція: переходить у корінь диска C:\, створює базовий каталог source_OS і три підкаталоги однойменною командою mkdir (аналог md).
2. attrib +H .hidden
Функція: змінює атрибути файлу чи каталогу. Параметр: +H (встановлює атрибут Hidden — прихований; для зняття використовується -H).
3. dir && dir /AH
Функція: виводить вміст каталогу. Звичайний dir не показує приховані об'єкти, а ключ /AH (/A — фільтр за атрибутом, H — Hidden) виводить тільки прихований каталог .hidden (рис. 1).
4. echo lab6 > labs\lab6.txt && echo lab7 > labs\lab7.txt
Функція: створює текстові файли за допомогою оператора перенаправлення стандартного потоку виводу > (перезаписує або створює новий файл і записує туди рядок).
5. type labs\lab6.txt && type labs\lab7.txt
Функція: команда type виводить текстовий вміст файлу в консоль (рис. 2). Якщо викликати type lab6.txt з C:\source_OS, система видасть помилку, бо файл лежить у підкаталозі labs.
6. copy con lects\lect6.txt [Ctrl+Z -> Enter] && copy con lects\lect5.txt [Ctrl+Z]
Функція: класичний спосіб створення файлу з потоку консолі (con — пристрій клавіатури). Оскільки після вводу команди ми одразу натискаємо комбінацію кінця файлу Ctrl+Z (символ ^Z / EOF), створюються порожні файли довжиною 0 байт (рис. 3).
7. echo %USERNAME% > .hidden\user6.txt
Функція: бере ім'я поточного користувача з системної змінної середовища %USERNAME% (Taras) і записує його у файл user6.txt всередині прихованого каталогу.
8. tree /f /a . > .hidden\tree6.txt
Функція: будує графічне дерево поточного каталогу (.) і зберігає у файл. Параметри: /f (виводити не лише папки, а й імена файлів у них), /a (використовувати ASCII-символи псевдографіки замість розширених символів, щоб у файлі не було кракозябр, рис. 4).
9. cd %USERPROFILE% && mkdir OS OS\links && cd OS
Функція: переходить у домашній каталог користувача (%USERPROFILE% = C:\Users\Taras) і створює каталог OS разом із вкладеним каталогом OS\links.
10. mklink /d lects C:\source_OS\lects
Функція: створює символічний зв'язок на каталог (Directory Symbolic Link, тип у dir — <SYMLINKD>). Параметр: /d (directory). Може вказувати на відносні шляхи, інші томи та мережеві папки UNC; вимагає прав адміністратора.
11. mklink /j labs C:\source_OS\labs
Функція: створює точку з'єднання каталогів (Directory Junction, тип у dir — <JUNCTION>). Параметр: /j (junction). Працює тільки для локальних каталогів і тільки з абсолютними шляхами (рис. 5–6).
12. type C:\source_OS\.hidden\user6.txt > result6.txt && echo 6 >> result6.txt
Функція: формує початок файлу result6.txt. Оператор з однією стрілкою > створює файл з іменем користувача (Taras), а подвійна стрілка >> дописує в кінець файлу номер варіанта 6 без затирання попередніх рядків.
13. echo. >> result6.txt && echo. >> result6.txt
Функція: команда echo. (із крапкою впритул до слова echo без пробілу!) виводить порожній рядок (переведення каретки CRLF). Дві команди поспіль додають 2 порожні рядки у result6.txt.
14. type labs\lab6.txt >> result6.txt && type labs\lab7.txt >> result6.txt
Функція: читає вміст файлів lab6.txt та lab7.txt через створений зв'язок-з'єднання labs і дописує їх у кінець result6.txt (рис. 7).
15. mklink /h links\tree6_h.txt C:\source_OS\.hidden\tree6.txt
Функція: створює жорсткий зв'язок (Hard Link) на файл. Параметр: /h (hardlink). Це не ярлик, а другий рівноправний запис у таблиці MFT (Master File Table) NTFS, що вказує на ті самі фізичні кластери даних (рис. 8).
16. fsutil hardlink list links\tree6_h.txt >> result6.txt
Функція: системна утиліта керування файловою системою fsutil з підкомандою hardlink list знаходить і виводить усі імена (жорсткі посилання) цього файлу на томі NTFS (\source_OS\.hidden\tree6.txt та \Users\Taras\OS\links\tree6_h.txt) і дописує їх у result6.txt (рис. 9).
17. cd C:\ && mkdir mount mount\NTFS_6 mount\FAT_6
Функція: створює порожні каталоги на томі NTFS, які слугуватимуть точками монтування для нових дискових томів (рис. 11).
18. diskpart /s C:\lab\dp6.txt
Функція: утиліта керування дисками і розділами. Ключ /s виконує пакетний сценарій (select disk 1, clean, convert mbr, create partition primary size=1000, format fs=ntfs label=NTFS_6 quick, create partition primary, format fs=fat32 label=FAT_6 quick, рис. 12).
19. mountvol C:\mount\NTFS_6 \\?\Volume{f8a0692a-0000-0000-0000-010000000000}\
Функція: монтує відформатований том без літери диска у порожню папку NTFS за його незмінним унікальним ідентифікатором \\?\Volume{GUID}\. Ключ /L виводить GUID змонтованого тому (рис. 13).
20. mklink /h C:\mount\FAT_6\... (Перевірка обмежень FAT32 і міжтомних зв'язків)

🎙️ ЩО КАЗАТИ ВИКЛАДАЧУ (СЦЕНАРІЙ ДОПОВІДІ)

Висновки: За допомогою утиліт командного рядка Windows (mkdir, attrib, copy con, tree, mklink, fsutil, diskpart, mountvol) створено і досліджено всі види об'єктів ФС для варіанта 6. Практично доведено, що з'єднання (Junction), символічні (Symlink) і жорсткі зв'язки (Hard Link) та точки монтування підтримуються виключно у файловій системі NTFS і відсутні у FAT32. При цьому Hard Link працює лише для файлів у межах одного тому, а Symlink може вказувати як на файли, так і на каталоги на інших томах. Дякую, готовий відповісти на питання!

1. Відмінність між базовим та динамічним дисками в ОС Windows.

Базовий диск (Basic Disk) використовує стандартну таблицю розділів MBR або GPT, містить основні розділи (Primary), розширений розділ (Extended) та логічні диски і сумісний з усіма ОС. Динамічний диск (Dynamic Disk) використовує приховану базу даних LDM (Logical Disk Manager) і дозволяє створювати томи, що охоплюють кілька фізичних дисків: прості, складені (Spanned), чергувальні (Striped / RAID-0), дзеркальні (Mirrored / RAID-1) та RAID-5.

2. Відмінність між поняттями «розділ» (partition) та «том» (volume) у ОС Windows.

Розділ (Partition) — це неперервна фізично виділена область секторів на одному конкретному фізичному диску, прописана в таблиці MBR/GPT. Том (Volume) — це логічна одиниця зберігання, відформатована під певну файлову систему (NTFS, FAT32), якій можна призначити літеру або точку монтування (том може складатися з кількох розділів на різних динамічних дисках, а розширений розділ MBR є розділом, але не є томом).

3. Яка файлова система в ОС Windows надає можливість використовувати її папки для монтування томів?

Тільки файлова система NTFS. Це реалізується через механізм точок повторної обробки (NTFS Reparse Points). Порожній каталог на томі NTFS стає точкою монтування іншого тому (при цьому сам змонтований том всередині цієї папки може мати будь-яку файлову систему — наприклад, NTFS або FAT32, як ми показали в роботі).

4. Яка відмінність у монтуванні томів за допомогою команд mountvol та mklink?

Команда mountvol працює безпосередньо з диспетчером монтування Windows (MountPointManager) і прив'язує цілий том за його унікальним ідентифікатором \?\Volume{GUID}\ до порожньої папки NTFS або літери диска. Команда mklink /J створює точку з'єднання (Directory Junction) на будь-який локальний каталог або корінь диска.

5. В чому переваги використання UID (GUID) тому, а не його літерного позначення?

По-перше, літер дисків в англійському алфавіті лише 26 (від A: до Z:), а томів на сервері може бути більше. По-друге, літера диска може змінитися при підключенні нових накопичувачів або перепризначенні адміністратором, через що шляхи зламаються. А унікальний ідентифікатор тому \?\Volume{GUID}\ прописаний у метаданих тому і залишається незмінним незалежно від літер і портів підключення.

6. У чому різниця між властивостями жорстких (Hard Link) та символічних зв’язків (Symbolic Link), з'єднань (Junction)? Для яких ФС можна використати зв'язування?

1) Жорсткий зв'язок (mklink /H): створюється тільки для файлів і тільки в межах одного тому NTFS; це друге ім'я того самого запису MFT; файл фізично видаляється лише тоді, коли видалені всі його жорсткі зв'язки. 2) З'єднання (mklink /J): працює тільки для каталогів на локальних томах цього ПК і зберігає лише абсолютний шлях. 3) Символічний зв'язок (mklink або mklink /D): універсальний файл-покажчик, працює і для файлів, і для каталогів, підтримує відносні шляхи, інші томи та мережеві кулі (SMB/UNC); якщо видалити оригінал, посилання стає «битим». Усі три види зв'язків працюють тільки на NTFS (у FAT32 їх немає).

💻 ПОЯСНЕННЯ КОДУ, ФУНКЦІЙ ТА ПАРАМЕТРІВ
1. gcc -O0 -pthread race_demo.c -o race_demo
Компіляція race_demo: прапорець -O0 вимикає оптимізацію компілятора, щоб операція counter++ гарантовано транслювалася у три окремі машинні інструкції LOAD / ADD / STORE у пам'яті, а не згорталася у регістр; -pthread підключає бібліотеку потоків POSIX.
2. pthread_create(&tid[t], NULL, worker, NULL); pthread_join(tid[t], NULL);
Керування потоками: pthread_create створює потік ядра ОС, що виконує функцію worker; pthread_join блокує головний потік main до завершення всіх робочих потоків.
3. pthread_mutex_lock(&lock); counter++; pthread_mutex_unlock(&lock);
Захист критичної секції м'ютексом (race_demo.c): pthread_mutex_lock атомарно захоплює замок (якщо він зайнятий — переводить потік у стан сну через системний виклик ядра futex), після інкременту pthread_mutex_unlock звільняє замок і будить чергу.
4. ./race_demo 4 1000000 та ./race_demo 4 1000000 --mutex
Запуск демонстрації гонитви: параметри 4 (кількість потоків), 1000000 (ітерацій на потік, очікувано 4 000 000). Без захисту втрачається ~65–71% інкрементів; з прапорцем --mutex втрачено 0 (OK).
5. int tmp = balance; usleep(20000); tmp += a->amount; balance = tmp;
Штучне розширення вікна гонитви (race_trace.c): між читанням балансу рахунку (100 грн) і записом вставлено затримку usleep(20000) (20 мс), щоб наочно побачити з мітками часу clock_gettime(CLOCK_MONOTONIC), як два банкомати затирають результат один одного (130 грн замість 180 грн).
6. ARM64: ldr x8, [x0] -> add x8, x8, #1 -> str x8, [x0] VS ldaddal x8, x8, [x0]
Дизасемблювання інкременту на ARM64 (asm_demo.c): звичайний (*c)++ компілюється у 3 інструкції (читання ldr, додавання add, запис str), між якими потік можуть перервати. Атомарний atomic_fetch_add — це одна неподільна інструкція процесора ARMv8.1 LSE ldaddal.
7. x86-64: mov (%rdi), %rax -> add $1, %rax -> mov %rax, (%rdi) VS lock addq $1, (%rdi)
Дизасемблювання на x86-64: атомарний інкремент використовує апаратний префікс шини/кешу lock addq, який утримує кеш-лінію процесора у монопольному стані протоколу когерентності MESI до завершення операції читання-модифікації-запису.
8. pthread_spin_lock(&spin); counter++; pthread_spin_unlock(&spin);
Спін-блокування (sync_bench.c, режим spin): на відміну від м'ютекса, потік не засинає в ядрі ОС, а крутиться в активному циклі опитування замка (busy-waiting), спалюючи процесорний час.
9. sem_init(&sem, 0, 1); sem_wait(&sem); counter++; sem_post(&sem);
Двійковий семафор Дейкстри (режим sem): sem_init ініціалізує семафор одиницею (0 — спільний для потоків одного процесу); sem_wait (операція P) зменшує лічильник з 1 до 0 (або блокує потік, якщо вже 0); sem_post (операція V) повертає 1.
10. atomic_fetch_add(&counter_a, 1);
Атомарна операція C11 (режим atomic): виконує апаратний атомарний інкремент змінної типу atomic_long без жодних викликів ядра ОС (швидше за м'ютекс у 2–4 рази).
11. volatile long local = 0; for(...) local++; pthread_mutex_lock(&mtx); counter += local; pthread_mutex_unlock(&mtx);
Локальне накопичення (режим local): кожен потік рахує у своїй приватній стек-змінній local без конкуренції за кеш-лінію, і лише 1 раз у кінці додає суму під м'ютексом (найшвидший спосіб — 2,4 мс проти 238 мс у м'ютекса!).
12. ./sync_bench <none|mutex|spin|sem|atomic|local> 4 1000000 [--csv]
Запуск бенчмарку синхронізації (серії E1–E5): тестує вказаний механізм на заданій кількості потоків та ітерацій; ключ --csv виводить рядок для автоматичного запису у таблицю.
13. sem_init(&empty, 0, N); sem_init(&full, 0, 0); // Буфер на N=8 комірок
Задача «Виробник–Споживач» (prodcons.c, серія E7): лічильний семафор empty = 8 рахує кількість вільних місць у кільцевому буфері, а full = 0 — кількість заповнених елементів.
14. put(): sem_wait(&empty); pthread_mutex_lock(&mtx); buffer[in]=item; in=(in+1)%N; pthread_mutex_unlock(&mtx); sem_post(&full);
Алгоритм виробника (prodcons.c): спочатку чекає вільну комірку (sem_wait(&empty)), потім під м'ютексом кладе елемент у буфер і сигналізує споживачам про появу даних (sem_post(&full)). У режимі none втрачається до 47% даних, у режимі sem — 0% втрат.
15. case 2 (fine_naive): pthread_mutex_lock(&acc_lock[from]); pthread_mutex_lock(&acc_lock[to]);
Взаємне блокування / Deadlock у моделі банку (bank.c, серія E8): коли Потік 1 переказує з рахунку A на B (бере замок A і чекає B), а Потік 2 одночасно переказує з B на A (бере замок B і чекає A), виникає циклічне очікування Коффмана — програма зависає у 10 з 10 запусків (фіксується сторожовим потоком watchdog через 1 с).
16. case 3 (fine_ordered): int lo = from < to ? from : to, hi = from < to ? to : from; lock(lo); lock(hi);
Усунення Deadlock впорядкуванням ресурсів (bank.c): ми порушуємо 4-ту умову Коффмана (циклічне очікування), завжди захоплюючи м'ютекси рахунків строго в порядку зростання їх індексу (lo -> hi). Результат: 0 взаємних блокувань і точне збереження суми банку 10 000 грн!
17. flag_p[me] = 1; turn_p = other; while (flag_p[other] && turn_p == other) ;
Класичний алгоритм Петерсона (peterson.c, серія E9): на сучасних багатоядерних процесорах у режимі plain (звичайні volatile змінні) взаємне виключення ламається у 100% запусків через апаратну перестановку Store->Load у буфері записів (Store Buffer).
18. atomic_store(&flag_a[me], 1); atomic_store(&turn_a, other); // memory_order_seq_cst
Виправлений алгоритм Петерсона (режим seq): використання атомарних операцій з повною послідовною узгодженістю memory_order_seq_cst вставляє бар'єри пам'яті і дає 0 порушень критичної секції.
19. Потік 1: X = 1; barrier(); r1 = Y; | Потік 2: Y = 1; barrier(); r2 = X;
Лакмус-тест Store Buffering (litmus_sb.c): перевіряє, чи можуть обидва потоки одночасно прочитати старі нулі (r1 == 0 && r2 == 0). Без апаратного бар'єру (none) цей «неможливий» результат виникає у 8,4% ітерацій на ARM64 та у 27,1% на x86-64!
20. atomic_thread_fence(memory_order_seq_cst); // ARM64: dmb ish, x86: mfence
Повний апаратний бар'єр пам'яті (litmus_sb fence): змушує процесор спочатку скинути буфер записів (Store Buffer) у кеш L1 до виконання наступного читання. Результат: 0 разів r1 = r2 = 0 з 1 000 000 ітерацій.
